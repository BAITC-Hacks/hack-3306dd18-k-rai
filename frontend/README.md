# Граф денег — фронтенд

Экран аналитика для кейса «Граф денег»: схема транзакционной сети с ролями узлов,
топ-листом приоритетов проверки, карточкой узла, AI-ассистентом и оценкой
устойчивости сети при изъятии топ-N узлов.

Весь интерфейс на русском. Все выводы сформулированы как **гипотезы для проверки**,
а не как утверждение о виновности.

## Запуск

```bash
npm install
npm run build     # статический экспорт в out/
npm start         # http://localhost:4174, статика и прокси /api/*
```

Сборка кладёт готовую статику в `out/`. Бэкенд раздаёт эту папку, и проект живёт
по одной ссылке — серверных возможностей Next.js здесь нет (`output: 'export'`).

Проверки:

```bash
npx tsc --noEmit                    # типы
npx eslint .                        # линт
npx tsx scripts/check-mock.ts       # структура моков соответствует брифу
npx tsx scripts/check-resilience.ts # метрики устойчивости сети
npx tsx scripts/check-frontend.ts   # поиск, API, отмена запросов и регрессии
npx tsx scripts/check-markdown.tsx  # форматирование ответов агента
npx tsx scripts/check-real-api.ts <graph.json> [resilience.json]  # сверка с бэкендом
```

> `npm run dev` для проверки не используется: команда не завершается.
> Чтобы посмотреть результат, соберите проект и раздайте `out/` любым статическим
> сервером, например `npx serve out`.

## Переменные окружения

| Переменная | Значение | Смысл |
| --- | --- | --- |
| `NEXT_PUBLIC_USE_MOCKS` | `false` (по умолчанию) / `true` | реальный API; моки включаются явно |
| `NEXT_PUBLIC_API_URL` | пусто по умолчанию | база API; пусто означает тот же origin |

Переменные читаются на этапе сборки, поэтому переключение на реальный бэкенд —
это пересборка:

```bash
NEXT_PUBLIC_USE_MOCKS=false npm run build
```

## Контракт с бэкендом

```
GET  {API}/api/graph   → GraphData
POST {API}/api/ask     → AskRequest → AskResponse
```

Типы — в [`lib/types.ts`](lib/types.ts). Всё остальное (соседи узла, статистика,
устойчивость сети) считается на клиенте.

### Сверено с реальным бэкендом

Контракт проверен против `https://financegraph-cofy.onrender.com` (FastAPI,
спека на `/openapi.json`, Swagger UI на `/docs`). Ответы совпадают с ТЗ по цифрам:
2 248 узлов, 3 119 рёбер, 81 seed, 444 обрыва, оборот 365 890 012 ₸.

Расхождения с брифом, которые фронт уже переваривает:

| Что | Реальность | Как обработано |
| --- | --- | --- |
| `top_gids` в кластерах | строка `"gid,gid,gid"`, а не массив | `gidList()` в `normalize.ts` разбирает обе формы |
| шаги агента | `{tool, result}` вместо `{tool, args, summary}`, `result` — массив записей | `stepSummary()` собирает фразу из массива, дамп JSON в интерфейс не попадает |
| `selected_gids` в `/api/ask` | в схеме нет, бэкенд поле игнорирует | отправляется по-прежнему: лишнее поле не ломает запрос, заработает без правок фронта |
| кластеров | 91, а не 5–6 | цвет кластера считается по золотому углу, палитра не заканчивается |
| `top` | 100 позиций, а не 20 | список показывает всё, что пришло (ТЗ требует «не менее 20») |
| доля пропуска | до 278× у 320 узлов | карточка показывает величину и объясняет, почему она недостоверна |
| gid | 18-значные, за пределами `MAX_SAFE_INTEGER` | проверено: все 2 248 переживают JSON → JS без искажений и без коллизий |

Есть ещё два эндпоинта, которые фронт **намеренно не использует**:
`/api/node/{gid}` — данные уже есть в `/api/graph`, лишний запрос на клик не нужен;
`/api/resilience` — устойчивость считается на клиенте, как требует бриф, поэтому
работает мгновенно и без сети. Результат сверен с бэкендом и совпадает
до последней цифры (см. `scripts/check-real-api.ts`).

### Проверка против живого API

У бэкенда нет заголовков `Access-Control-Allow-Origin`, поэтому напрямую с другого
origin браузер запрос заблокирует. В бою это не мешает — бэкенд раздаёт `out/`, и
origin общий. Локально ту же топологию повторяет прокси:

```bash
NEXT_PUBLIC_USE_MOCKS=false npm run build
node scripts/serve-with-api.mjs --api https://financegraph-cofy.onrender.com --port 4174
```

Сверка нормализации и метрик с сохранённым ответом бэкенда:

```bash
npx tsx scripts/check-real-api.ts graph.json resilience.json
```

Любой ответ бэкенда проходит через [`lib/normalize.ts`](lib/normalize.ts): он
проверяет поля, принимает частые синонимы (`gid`/`id`, `src`/`source`,
`sum`/`sum_kzt`) и подставляет безопасные значения по умолчанию, чтобы
переименованное или отсутствующее поле не роняло интерфейс. Если бэк не прислал
`top`, он считается на клиенте из `priority_score`; если не прислал `is_cutoff` —
выводится из данных (4-е колено без исходящих).

Запрос к агенту ограничен таймаутом 45 секунд через `AbortController`.

## Структура

```
app/page.tsx              экран целиком: состояние, сцены, раскладка
components/GraphCanvas    обёртка над react-force-graph-2d (только клиент)
components/SidePanel      три вкладки: Приоритеты | Узел | Агент
components/NodeCard       карточка узла: цифры, evidence, кто платил / кому платил
components/PriorityList   топ-20 с фильтром по роли
components/AgentPanel     вопрос агенту, шаги, ответ, подсветка
components/ResilienceCard «до → после» при изъятии топ-N
components/Legend         легенда ролей и счётчики
lib/mock.ts               детерминированный генератор данных (seed 42)
lib/graph.ts              индекс соседей и статистика, считается один раз
lib/resilience.ts         union-find: компоненты, крупнейшая компонента, доля оборота
```

### Почему GraphCanvas — отдельная обёртка

`react-force-graph-2d` обращается к `window` и падает на сервере. Поэтому
`ForceGraph2D` импортируется внутри `GraphCanvas.tsx` обычным импортом, ref живёт
там же, а страница подключает саму обёртку через
`dynamic(() => import('@/components/GraphCanvas'), { ssr: false })`. Наружу
обёртка отдаёт `focusNode`, `zoomToNodes` и `zoomToFit` через
`useImperativeHandle` — передавать ref через `dynamic` напрямую нельзя, он
теряется.

### Почему раскрытие колен не ломает раскладку

При смене колена фильтруются **исходные массивы** `nodes` и `links`, а объекты
узлов не пересоздаются: симуляция сохраняет координаты `x`/`y`, которые
`react-force-graph` кладёт прямо в объекты. Ребро показывается, только если видимы
оба его конца. Рёбра, наоборот, пересобираются в чистые `{source, target}`, потому
что после старта симуляции библиотека подменяет их концы объектами узлов — для
этого везде используется `endpointId()` из `lib/graph.ts`.

Частицы (`linkDirectionalParticles`) включаются только на подсвеченных рёбрах или
рёбрах выбранного узла: на тысячах рёбер сплошная анимация кладёт кадровую частоту.

## Режим моков

`lib/mock.ts` — детерминированный генератор (mulberry32, seed 42): при
перезагрузке граф тот же. Структура повторяет реальную выгрузку в масштабе ~1:5,4:

- 415 узлов по коленам 30 / 84 / 82 / 140 / 79, около 765 рёбер;
- 8 seed-клиентов без исходящих переводов — как 19 из 81 в реальных данных;
- 3 точки консолидации с 10–12 разными плательщиками;
- 2 распределителя с 33–34 получателями;
- транзитные цепочки и координатор, куда сходятся цепочки нескольких seed;
- все узлы 4-го колена без исходящих и с `is_cutoff: true`;
- 6 кластеров, топ-20 по `priority_score`.

Важно: роли и приоритеты в моках **не зашиты списком gid**. Генератор строит
топологию и денежные потоки, затем метрики (`in_senders`, `out_receivers`,
`sum_in`, `sum_out`, число достигающих узел seed-клиентов) вычисляются из рёбер, и
только потом применяются правила ролей. `evidence` собирается из этих же цифр.

### Правила присвоения ролей

Порядок проверки важен: побеждает первое подошедшее правило.

| Роль | Правило |
| --- | --- |
| узел на обрыве | `depth = 4` и нет исходящих → судим только по входящим: `in_senders ≥ 8` даёт консолидатора с пониженной уверенностью, иначе периферия |
| consolidator | `in_senders ≥ 8` и доля пропуска `< 0.5` |
| distributor | `out_receivers ≥ 20` |
| coordinator | узел достигается цепочками от `≥ 3` seed, `in_senders ≥ 3`, доля пропуска `< 0.35`, входящие в верхних 5% графа |
| transit | доля пропуска в диапазоне `0.8…1.2` при наличии входящих и исходящих |
| terminal | исходящих нет, входящие есть, **и узел не на обрыве выгрузки** |
| peripheral | всё остальное |

`priority_score` — взвешенная сумма перцентильных рангов (входящая сумма 0,30;
плательщики 0,22; исходящая сумма 0,15; число достигающих seed 0,15) плюс вес роли
0,18, нормированная на максимум.

### Учёт обрыва выгрузки

444 узла 4-го колена в реальных данных имеют нулевые исходящие — это артефакт
обхода, а не «деньги осели». Поэтому:

- роль `terminal` таким узлам не присваивается в принципе;
- правила, опирающиеся на долю пропуска, к ним не применяются: их исходящие не
  отсутствуют, а лежат за границей выгрузки;
- на холсте они рисуются пунктирным контуром с прозрачностью 35%;
- в карточке показывается пояснение, почему узел не считается конечным получателем.

## Устойчивость сети

`lib/resilience.ts` считает на клиенте, без захардкоженных цифр:

- число слабосвязных компонент (union-find, направление рёбер игнорируется);
- размер крупнейшей компоненты;
- долю оборота, прошедшую через изъятые узлы: сумма `sum_kzt` рёбер, где изъятый
  узел источник или получатель, делённая на общий оборот.

Всё показывается в формате «до → после». Кнопка «Вернуть» восстанавливает сеть.

## Доступность и аккуратность

- Цвет никогда не единственный признак: рядом с каждым цветом стоит подпись роли.
- Числа набраны табличными цифрами, суммы — в формате `1 250 000 ₸`.
- `prefers-reduced-motion` отключает частицы и анимацию раскрытия колен: колена
  открываются сразу, камера не летит.
- Фокус клавиатуры видимый, вкладки размечены ролями `tab` / `tabpanel`.
- Интерфейс не выдумывает данных, которых нет в ответе бэкенда: ни имён, ни
  возрастов, ни городов.
